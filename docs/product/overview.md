# LAMP 소개

## 무엇을 해결하는가

금융 접속·실시간 서비스와 IoT/Edge 시스템에서는 네트워크 연결, 데이터 형식, 서비스 간 전달, 세션 제어, 장애 감지, 배포·운영 관리를 각 애플리케이션이 반복적으로 구현하기 쉽습니다. LAMP는 이러한 공통 영역을 플랫폼으로 두고, 서비스 개발자가 도메인 기능 구현에 집중하도록 구성합니다.

**Lightweight Adaptive Microservices Platform**라는 이름은 작고 명료한 공통 실행 계층, 다양한 연결·배포 환경에 대한 적응성, 서비스 단위의 조합·운영이라는 설계 지향을 나타냅니다. 'Lightweight'가 타 플랫폼 대비 객관적 자원 우위를 입증한 성능 수치를 의미하지는 않습니다.

## 세 가지 관점

1. **개발:** 트랜잭션 및 스키마 정의, 코드 생성, 플러그인 로직과 서비스 Hook 작성.
2. **실행:** 외부 프로토콜을 내부 Message 모델로 수렴시키고 URI 체인에 따라 연결하거나 플러그인을 실행.
3. **운영:** 서비스 배치·상태와 구성 변경을 Control Plane에서 다루고, 처리 계층과 분리하여 관리.

## 구성 제품군

| 구성요소 | 역할 | 대외 문서 범위 |
|---|---|---|
| LAMP Core | 공통 메시지·요청 파이프라인·프로세스 실행 | 플랫폼의 개념과 개발 인터페이스 |
| LAMP Manager | 배포 및 서비스 운영 관리 UI | 기능 개요만 |
| LAMP Studio | 스키마·트랜잭션·플러그인 개발 워크플로 | 개념 및 작업 흐름 |
| LAMP Client SDK | 클라이언트 연동 | 설계 계약 및 접근 조건 |
| LAMP Financial | 금융 도메인 공통 확장 | 적용 사례 수준, 고객사 정보 제외 |
| IoT Protocol Bridges (계획) | MQTT, BLE 등 외부 장치·브로커 연계 확장 | 로드맵/개념 설계만; 구현·지원 확정 아님 |

## 적합성 검토

장기 연결 기반 API, 플러그인 단위의 기능 전개, 기존 금융 시스템 연결, 자체 제어 영역과 Kubernetes 배포 모델을 구분하려는 조직에 유용한 구조입니다. 다만 실제 도입에는 목표 TPS, 접속 수, 장애 복구 목표, 보안 위협 모델, 운영체제 및 의존성 검증이 선행되어야 합니다.
